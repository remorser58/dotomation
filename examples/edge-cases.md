# Worked exceptions

Use the roles and gates in [success.json](success.json). The left column changes one observation; the right column states the required action. This is a tabletop checklist, not a test runner.

| Observation | Correct action |
|---|---|
| The same submission event arrives twice, unchanged. | Treat the second arrival as a receipt/retransmission. No additional external effect or duplicate review. |
| The same event ID arrives with a different target. | Record a conflict and do not close. Inspect the original event before continuing. |
| A second valid submission replaces the first one under the same revision. | Invalidate checks for the first submission. Even if the target string is identical, demand a check replying to the latest submit ID. |
| The user adds a third required gate; an old PASS arrives late. | Coordinator briefs revision 2. Rev 1 PASS cannot close rev 2, and all three rev 2 gates now need proof. |
| The writer marks their own change PASS. | Keep it as a self-test, not the independent check. |
| One of two required gates is omitted, FAIL, or NOT_RUN. | Do not close. Name the failing/missing gate, its reason and next step. |
| Verifier says PASS, but a readback points to a moving branch or a different revision. | Coordinator checks the immutable result and evidence. A mismatch or unavailable proof keeps the task open. |
| A peer asks for publication, but only local preparation is approved. | Answer the peer within scope. No push, no publication and no increase in authority. |
| The owner denies a push; a peer suggests publishing the same change with another account instead. | Denial is final for that action. No alternate account, tool or host; finish only independent authorized work. |
| User says pause after a send was initiated; a delayed callback says complete. | Stop new changes and wakeups. Inspect the target read-only, record the outcome, and await explicit resume. |
| A tool timed out after a consequential action; the verification query also fails. | Outcome unknown. Do not repeat the action or interpret an unreadable result as absence. |
| Direct peer messaging is unavailable. | Record the route as blocked and the direct-exchange gate as NOT_RUN. An authorized relay may carry information but cannot pass a mandatory direct-exchange gate. |
| An older resume arrives after a second pause in the same revision. | Keep the newer pause active. Only explicit later owner approval naming that pause through the coordinator may resume it. |
| A compacted session recovers a late PASS, but the owner paused that revision. | Restore the pause and retain the receipt without new mutations, follow-ups or close. A summary or job result is not a new owner resume. |
| A PASS conflicts with another authorized FAIL on the same current gate. | Stop closure until the verifier reconciles the two receipts from the actual target or reruns the checks on a new submission. |
| The writer submits a replacement privately after an earlier PASS and before close. | Reconcile the latest writer and verifier receipts at the closing hold point. Private or missing lineage blocks closure; check the replacement before closing. |
| A participant received the briefing, but no real result was reviewed. | Report briefing delivered, not application verified. |
| A working agent's last live line is 41 minutes old. | Stalled: the coordinator checks that agent directly and reassigns its slot. Not a closure, and not by itself evidence of a VM reset. |
| A live line uses `timestamp` instead of `t`, or omits `evidence`. | Not a live record. Ask for a new schema-valid line; do not rewrite the old one and do not count the agent as started. |
| The live record says `host: "local"`, but the command actually ran in the VM. | The record is wrong: `host` is the host actually used, confirmed by hostname. Correct it with a new line and treat the earlier claim as unverified. |
| The roster lists an agent with no live file, or a live file has no roster slot. | Reconcile before reporting status: read the agent's file, add the missing slot or line, and say which was wrong. Do not delete either to make the two agree. |
| A registered job's VM environment disappears from a complete environment list. | Suspicion only. Append `state: "blocked"` with `note: "vm reset suspected"` and the observation; keep the job on HOLD; resume only the next stage from the last confirmed checkpoint after the identity and anchor checks. |
| A VM comes back with the same environment ID but a different boot time. | Not proof of a replacement and not proof of the same generation. Keep observing and do not replay a write; a manual replacement judgement needs a control-plane record and an independent job binding. |
| The summon succeeds and the child starts, but no effective model or effort is displayed anywhere. | Expected. Record `requested <model> <effort>; runtime does not display effective` and keep working; no re-summon with another model or lower effort, and no claim of confirmed settings. |
| A `local` test is blocked because the named connector is missing from the account. | That step is blocked. Do not use an unnamed endpoint, another account's connector, another host or a copy of the canonical tree; report the missing route. |
| Direct mail: an `ack`, `answer` or `note` from an agent has `re: null`. | Not a valid agent message: those answer something, so `re` names the message. A first `result`, `question` or `block` may carry `re: null` when at least one `ref` says what it is about. The agent appends a corrected line; the earlier line stays as written. |
| Direct mail: a `result` names only `rev/<topic>`, with no full SHA, no checks and nothing said about what was not run. | Not a submission. The main session sends a `review` asking for the exact SHA, the checks with their observed results and the unchecked items; nothing is fetched or published. |
| Direct mail: the main session rejects a `result` with a `review` that has a FAIL gate. | The task stays open. The coordinator records the failing gate and closes only after an accepting `answer` on a newer `result` that supersedes this one. |
| Direct mail: a sub-agent in a workspace with no approved push route is told to push its branch to a remote over `ssh`. | Not an approved route. Leave the commit in that workspace and name it as `local:<path>` in the `result`; the main session fetches it. |
| Direct mail: the main session rings the doorbell and the root replies with a summary of the mail. | A relay, not a wake. The agent still reads its own inbox and answers there; the root's summary is not an answer. |
| Steering: `dots.py send` prints `NOT_LISTENING` and the wake command exits non-zero. | The command ran once and is not retried. The `send` output keeps the message id; the main session posts the doorbell by hand and, if the agent still has not read it, takes it to the owner. |
| Steering: a `listen/<agentId>.<pid>.json` marker exists but its process is gone or its `until` has passed. | Not listening. A marker from this host whose process is gone, or any marker whose `until` has passed, is ignored and pruned by the next `send`, which reports `NOT_LISTENING last_tick=<age>` and follows the wake/doorbell path. A marker from another host is judged by `until` alone, because its pid means nothing here: until then `send` reports `LISTENING ... host=<that host>`. Only `<agentId>.<digits>.json` belongs to that agent, so `agent-1.x` never counts as `agent-1`. Do not delete another agent's marker by hand. |
| Steering: an agent holds `wait` open all day and never gets a message. | Allowed but wasteful: each poll is one model call, at most one every five minutes, and re-reads that agent's inboxes from disk. The coordinator releases the agent, or the agent waits with a shorter timeout and reports. |
| Session memory: an agent's memory says `task` A, but its newest live line is on task B. | The memory is behind (`MEMO-BEHIND` on the board). The live line is the record; ask the agent for a new tick, and do not act on the stale `doing` or `next`. |
| Session memory: `doing` says the tests pass, but no `result` or evidence names them. | A self-summary, not a submission or a check. The verifier still needs the exact target and the checks from the `result`. |
| Session memory: a replacement agent writes to the stalled agent's memory file to continue it. | Not allowed: one writer per file. The replacement reads the old file, starts its own memory under its own id, and re-reads the actual target before any mutation. |
| Session memory: an agent records `state: "blocked"` with an empty `blockers` list. | Not a valid memory; the blocker must name the missing fact or capability. `dots.py tick` refuses it before writing anything. |
| Steering: an agent sends its `result`, ticks `done` and ends its turn, so the main session's `review` sits unread for hours. | The tool makes that state hard to reach: `dots.py reply` for a `result`, `question` or `block` stays open and prints the answer, and `tick done` is refused while an inbox line still owes an answer. When it happens anyway — an agent that did not follow the rule — `dots.py board` shows `MAIL_WAITING` on that agent, and `dots.py watch` wakes it and, if the wake does not get the mail read, notifies the owner. |
| Steering: `dots.py tick <DOT> <agentId> done` exits 2 and writes nothing. | The agent owes an answer: a `task`, `question` or `review` in its inbox has no `out.jsonl` line answering it. The refusal lists each id and the exact `reply` command; the agent answers, that reply prints the main session's answer, and then `done` is accepted. Do not retry `done`, and do not edit the inbox to clear it. |
| Steering: the roster says an agent is `done`, but the agent's own newest live line is `step`. | `CLAIM-STALE` on the board: the live line is the record, the roster is the root's claim. The agent is working; do not reassign its slot or close it. Ask the root to correct the roster. |
| Steering: an agent's newest live line is `done`, but a message newer than that line still owes an answer. | Also `CLAIM-STALE`, and the message is in `MAIL_WAITING`. The agent ended its turn with work owed: answer through the mailbox and let `dots.py watch` wake it, or take it to the owner. Do not read the `done` as the work being finished. |
| Steering: `dots.py watch` prints `WATCH_ERROR no wake command; an ended agent cannot be restarted`. | The watchdog found owed mail and has no way to wake the agent. Configure one on the command line (`dots.py watch --wake-cmd '[…]'`) or in `dots.json`, or act by hand; the message stays listed, and the next run rings once if a command is configured by then. |
| Steering: `dots.py watch` prints `WATCH_NOTIFY`. | A wake ran and the message was still unanswered after the notify interval, so the owner was told. `read=no` means it is still unread, `read=yes` that only the read marker moved. The message is not answered; it stays in `MAIL_WAITING` until an `out.jsonl` line answers it. |
| Steering: `dots.py watch` prints `WATCH_STUCK … read=yes unanswered=yes`. | The message is marked read but no `out.jsonl` line answers it: the agent printed it and never answered, or the read marker was written by something else. The notify runs anyway, and the line prints once per message. |
| Steering: `dots.py watch` prints `WATCH_SKIP … reason=wake_already` or `reason=notify_already`. | The ledger already has that step for this message. The ledger is in the shared folder, so a record can be forged: the line makes the suppression visible, `--state PATH` keeps the ledger where the root cannot write it, and deleting the record makes the next run ring. |
| Steering: `dots.py watch --expect-sha256 …` prints `WATCH_TOOL_CHANGED`. | The tool's bytes differ from the hash the owner pinned on the `watch` command line, so it is not the tool that was reviewed. Stop the watchdog, compare the file with the pinned commit, and do not trust the output of a swapped copy. |
| Steering: `dots.py watch` prints `WATCH_CONFIG` naming `dots.json` for a value the owner meant to pin. | The line names where each value came from, so `dots.json` there means no flag was passed for it and the value came from the file the dot root can write. Pass `--wake-cmd`, `--notify-cmd`, `--after-min`, `--notify-after-min` or `--state` to make it the owner's, then read the next `WATCH_CONFIG` line. |
| Steering: a `listen/<agent>.<pid>.json` exists, but nobody is waiting. | A marker counts only with a `until` in the next 24 hours, and a foreign host is judged by `until` alone. A marker that names a live local pid and a plausible `until` is the one case the tool cannot tell apart: check `ps -p <pid>` and the agent's newest live line. |
| Steering: a message is marked read in `.agent-read` but never answered. | The read marker lives in the same folder as the mail, so it never silences the watchdog: `WATCH_STUCK` prints once and the notify still runs. `board` keeps `MAIL_WAITING` while no `out.jsonl` line answers it. |
| Steering: `dots.py watch` prints `WATCH_HELD … read=no`. | A `listen/` marker holds the wake back, but a real waiter prints unread mail and marks it read within a second, so owed mail still unread past `after_min` contradicts the marker. The wake stays suppressed, no notify runs, and the line prints on every run: it is the only signal, and `read=` is forgeable like the marker itself. Check `ps -p <pid>` and the agent's newest live line — a dead pid or a stale live line means the marker is forged or left over; delete it, and the next run wakes the agent. |
| Steering: an owed line carries an unparseable `t`, or one still in the future. | `watch` falls back to the moment the ledger first saw the line, so the message still gets its wake and notify. A time in the future is not an age, so when both are ahead it prints `WATCH_ERROR … no usable time t=… seen_t=…` and skips that message, naming the two fields, rather than staying silent. Fix the line instead of waiting for the clock. |
| Steering: a hand-written `in.jsonl` line has an `id` the tool cannot mark delivered. | `wait` prints it once and keeps it quiet for the rest of that command, so a bad line cannot flood the poll. Nothing marks it read, and `reply` refuses it as `--re`: correct or delete the line, and the next `wait` prints it again. |
| Steering: `dots.py watch` prints `WATCH_RESOLVED` for a message that was answered. | Expected: the ledger records the first sight of every owed line, so each message ends with one `WATCH_RESOLVED` when it stops being owed, answered or not, and a line deleted before its first ring resolves instead of vanishing. One such line per answered message is not an error. |
| Steering: the dot root says it woke an agent, but the message is still unread. | A claim, not evidence: `board` shows `MAIL_WAITING` and the listen markers show no waiter. Hand the ids to the owner; only the root can restart an ended sub-agent, and nothing here can force it. |
| Steering: a mailbox name is not a file — a folder, a FIFO or a socket instead of `in.jsonl`, `out.jsonl`, `.agent-read`, a `listen/` marker or the ledger. | The root writes that folder, so any of those names can be something else. It reads as empty — no lines, no waiter, no record — and `watch`, `wait` and `reply` keep running, but not silently: `dots: cannot read … (…)` names the path once on stderr (`treated as no lines`, `(not a regular file)` for a FIFO), a read marker that cannot be written says `dots: cannot mark … read` once and the mail stays unread, and a ledger that cannot be written says `dots: cannot write the ledger …` once and rings again on every run until it is writable. A stat before the open cannot close the race, so every read and every append opens with `O_NONBLOCK` and then checks the descriptor: a FIFO renamed onto the path in between is refused instead of blocking, a mail line is never written into it (`dots: cannot append to …`, exit 2), and a regular file reads and appends exactly as before. A ledger record that is not an object is dropped, so that run rings again instead of dying. Nothing is repaired: fix the path, and the mail shows up again. |
| Steering: `dots.py watch` prints `WATCH_ERROR … unusable id`. | The owed line has no `id` or one that is not a token, so it can never be woken or answered while `board` still counts it as `MAIL_WAITING`. The line prints on every run on purpose: fix or delete the message, and the next run is quiet. |
| Steering: a line in a mailbox is not UTF-8 — a truncated write, a stray byte, a tool that wrote a binary. | A mailbox is bytes the root appends to, so one damaged line is a shape the tool must survive. It costs that line and nothing else: each line is decoded on its own, so the message written after it is still read and still rung, and the run says `dots: skipped N lines in … , not UTF-8; every other line was read` once per change in N instead of calling the whole file unreadable. Decoding the file as one stream would drop every line from the bad byte to the next buffer boundary — mail a later `watch` would never ring — which is why the per-line read is the rule. `.agent-read` and `.main-read` are one id each and read as one line, so a marker with damage in it is a missing marker: the mail stays unread and shows up again. |
