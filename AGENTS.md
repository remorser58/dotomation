# Maintainer notes

This repository supports two user-selectable operating modes — **Mode 1 (`dots-only`)** in `modes/dots-only/` (Dots quota only, zero local quota) and **Mode 2 (`sub-dots`)** in `modes/sub-dots/` + `tools/subdots.py` (reverse `web-gpt-agent` local-to-subagent steering) — alongside the instruction-only Dots skill and the four owner-requested Python 3 stdlib tools below. The skill's entry point is [.agents/skills/dotomation/SKILL.md](.agents/skills/dotomation/SKILL.md); read it and [dispatch](workflows/dispatch.md) before editing the kit. Dispatch supplies the common Dots run and workspace requirements; role and workflow instructions must preserve them in downstream briefs. The JSON Schema in `protocol/` defines message shape, not authorization or ordering. Keep `examples/` consistent with both. Preserve stable protocol identifiers; introduce a new version for incompatible changes.

Verification: read the final skill, match the worked conversation to the schema, then test negative cases against the closure rules using approved existing tools. Use only synthetic evidence in examples. No install, third-party dependency, system service, account, credential or telemetry is part of this repository, with the owner-requested exceptions below. Do not publish or push without authorization.

## The first exception: `tools/dots_monitor.py`

The owner asked for a way to see whether a dot and its sub-agents are actually working, and self-reports alone cannot show that. That request, and only that one, is the first exception to the rule above:

- **What it is.** One read-only Python 3 file, `tools/dots_monitor.py` ([monitoring](workflows/monitoring.md)), with its standard-library test `tools/test_dots_monitor.py` and one JSON config template, `tools/dots-monitor.example.json`, holding host names, paths, account numbers and repository names only. An instance keeps its filled-in config outside this repository. It reads the live records, the Web GPT Agent daemon request log of each dot's account, and GitHub references through `gh api`. `watch` is a foreground command the reader starts and stops; nothing schedules or restarts it.
- **Still not part of this repository:** no install step, no package or dependency, no service, daemon, scheduler, hook, plugin, account, credential or telemetry. Standard library only, plus `ssh` and `gh` as existing CLIs the reader already has.
- **Read-only everywhere.** It never appends, edits, deletes or renames a record and never writes to a host it reads; the remote side runs only `wc -c` and `tail -c` over the configured files. It never messages a dot and never assigns work: it reports, and a coordinator still decides.
- **Bounded and redacted.** Every subprocess has a timeout, every file read is a byte tail, and anything that looks like a token is redacted before display.

## The second exception: `tools/dots.py`

The owner asked for a way to steer a dot's sub-agent from their own local session and to set that up for any user with one local machine ("하고 슈퍼킷에 세팅해라. 남들이 그냥 바로 써도 자기 환경에 맞춰서 쓸 수 있게"). Conversations inside a dot cannot be read or written from outside it, so the only possible route is a file the agent reads plus a command the agent holds open. That request, and only that one, is the second exception:

- **What it is.** One Python 3 file, `tools/dots.py` ([direct mail](workflows/direct-mail.md#steering-send-wait-reply), [session memory](workflows/session-memory.md#one-call-per-step)), with its standard-library test `tools/test_dots.py`. `tick`, `board` and `memo` keep the live record, the session memory and the mail read in one call; `send`, `inbox`, `read`, `reply` and `wait` carry direct mail, and `reply` for a `result`, `question` or `block` continues into the same loop `wait` runs so the answer is that command's output; `init` writes the instance config `<base>/dots.json` and creates the folder tree, then prints the brief to paste to each dot root; `watch` is the owner's fallback for owed mail whose agent holds no wait.
- **Still not part of this repository:** no install step, no package or dependency, no service, daemon, scheduler, hook, plugin, account, credential or telemetry. Standard library only. Every process the tool starts is one an agent or the user started, and it ends by itself: `wait` and a waiting `reply` exit 0 on mail, 3 on their timeout or 4 on a signal; the wake command `send` may run has a 25-second timeout and is never retried; `watch --loop 0` runs once and a loop only sleeps between runs until a signal ends it. No `cron`, launch agent, systemd unit or hook is installed or documented.
- **Protocol unchanged.** It writes only [mail-v1](protocol/mail-v1.schema.json), [live-record-v1](protocol/live-record-v1.schema.json) and [memory-v1](protocol/memory-v1.schema.json) shapes, plus the read markers, its own `listen/` markers, `dots.json`, its own watchdog ledger (`watch/state.json`, or `--state PATH`, which nothing else reads), the update stamp `<base>/.update-check.json`, and, when it updates, its own file and the `dots.py.bak-<old version>` beside it. A line written by hand or by an instance's own helper stays readable, and the tool reads them the same way. No new kind, field or protocol version.
- **Its own limits.** It is not a message broker and not a watcher service: `send` reports whether the agent is listening and otherwise runs `--wake-cmd` / `DOTS_WAKE_CMD` or prints the doorbell; root-writable `dots.json` hook commands (`wake`/`notify`) are ignored by default unless `DOTS_TRUST_CONFIG_CMDS=1` is set by the owner. `watch` is one more foreground command the owner starts, its flags win over `dots.json` because that file sits in the folder the root writes, and its ledger may only add a `WATCH_SKIP` line, never hide a ring. The tool cannot restart an ended sub-agent by itself — only the dot root can — so `watch` runs an owner-configured wake command and otherwise says `WATCH_ERROR` instead of pretending. `wait` polls about once a second while an agent holds it open, and the cost of that (one model call per poll, at most one every five minutes) is stated where the agent reads it.
- **Updates.** The owner asked that the kit's users get new versions without doing anything ("자동 업데이트 이런 것도 해두고", "나 말고 이거 사용자들"). That request is the only network access the tool makes on its own. After a command returns, writable standalone copies check the public `remorser58/dotomation` GitHub release at most once per 24 hours using `<base>/.update-check.json`, validate the SHA-256 and Python source, and replace only the tool itself, keeping `dots.py.bak-<old version>`. The kit's own checkout (`tools/dots.py` beside the repository's `.git`) only reports availability. `watch` never checks, and `DOTS_AUTO_UPDATE=0` or `"auto_update": false` in `dots.json` disables automatic checks. The shared config cannot set the update source; `DOTS_UPDATE_URL` is an environment-only test override. `dots.py update [--check]` is an explicit check, unaffected by opt-outs and the daily stamp. The release workflow publishes the release assets (`dots.py`, `subdots.py`, and their `.sha256` files) only on a matching version tag.

Any other executable, service or write path is still out of scope. If a future change needs one, it needs its own decision from the owner, not this paragraph.

## The third exception: `tools/subdots.py` (Mode 2: `sub-dots`)

The owner asked to split the repository into two selectable modes — Mode 1 (`dots-only`) and Mode 2 (`sub-dots`) — and to build Mode 2 as the inverse of `web-gpt-agent`: local main session -> local Reverse Bridge Hub -> Dots internal sub-agent, without routing through the Dots root, with active anti-death and anti-spin harnessing:

- **What it is.** One Python 3.9+ standard-library file, [`tools/subdots.py`](tools/subdots.py) ([`modes/sub-dots/README.md`](modes/sub-dots/README.md), [`modes/sub-dots/PROTOCOL.md`](modes/sub-dots/PROTOCOL.md)), with its standard-library test `tools/test_subdots.py`. It hosts an owner-private Hub (`~/.subdots` mode `0700`, SQLite WAL `0600` ledger, `hub.lock`, Unix control socket `0600`, loopback HTTP + Reverse Streamable-HTTP MCP server `/<token>/mcp` and per-agent `/a/<agent_token>/mcp`, plus local `mcp-stdio`), a local steering CLI (`provision`, `send`, `steer`, `ask`, `pause`, `resume`, `cancel`, `release`, `wake`, `events`), and the sub-agent harness client (`agent register|wait|step|reply|exec|ack|heartbeat`).
- **Standard library only, explicit lifecycle.** No external package, no `cron`/launchd/systemd installation, and no secret credentials stored in the repo. `hub start` / `hub stop` is started and stopped explicitly by the owner; optional `.dots-ops/` mirroring uses `O_NONBLOCK` + `S_ISREG` checks so root-writable folders cannot wedge the Hub.

## The fourth exception: `tools/dots_pilot.py`

The owner asked to eliminate external LLM coordinator daemons and personal AI tokens so a single checkout of this repository can bootstrap and sustain multi-track autonomous Mode 1 (`dots-only`) execution deterministically:

- **What it is.** One Python 3.9+ standard-library file, [`tools/dots_pilot.py`](tools/dots_pilot.py), with template [`tools/dots-pilot.example.json`](tools/dots-pilot.example.json) and unit suite `tools/test_dots_pilot.py`. It stores owner-private state in `~/.dotomation-pilot` (`0700`/`0600` + `flock`), pins `tools/dots.py` by SHA-256, initializes `dots.py loop` track presets (`generic`, `research-3track`, `ux-ui-impl-3track`), drives single-instance `dots.py watch --loop 0` cycles via per-run cryptographic sentinel nonces, reads `tools/dots_monitor.py` daemon health (`retained_limit_hit`, `start_churn`), and optionally invokes a cooldown-guarded daemon restart or HTTPS env-var webhook notify.
- **Zero AI tokens & no auto-installed services.** Uses zero personal AI tokens, zero personal URLs, and zero third-party packages. `once` and foreground `run` are started explicitly by the owner; `daemon_health.heal` is strictly opt-in behind a cooldown guard; `render-service --target launchd|systemd` only prints a service template on stdout and never installs launchd/systemd/cron jobs automatically.
